> 学习方式：以现有工程为参考，先理解设计目的，再亲手逐步重写，通过检查和追问把原理弄明白。

目标：复原现有 `bsp_eeprom.h` 和 `bsp_eeprom.c` 的功能，能解释模块职责、接口设计、边界处理和调用过程。当前参考方案是阻塞式 I²C，包含 7 个公共接口和 1 个私有状态转换工具。

## 如何使用这份大纲

1. 先看整体功能，再只做当前一个小任务。
2. AI 说明功能、设计理由和工程约束；你决定函数参数、返回值、数据类型和实现方式。
3. 默认不提供完整代码或逐项接口答案。需要帮助时，先指出卡点，再提示相关概念或 HAL 功能。

**设计接口时，自己回答：** APP 想做什么？调用时缺哪些信息？哪些信息已经由驱动保存？调用后 APP 需要知道什么？谁拥有数据，数据需要有效到什么时候？

保留当前芯片、编译器和调用关系。暂不增加 DMA、中断读写、异步状态机或新的持久化方案。原版是参考依据，发现问题要区分“原版行为”“复原错误”和“待优化项”。

## 第 1 步：梳理器件需求和驱动边界

**设计目的：** 明确驱动要处理哪些硬件限制，哪些决策属于 APP。

**逐轮小步：**

| 小步 | 本轮目标 | 检查点 |
| --- | --- | --- |
| 1.1 | 区分设备地址、EEPROM存储地址、RAM结果地址 | 能分别说明选芯片、选位置、存结果 |
| 1.2 | 理解开漏、START/STOP、数据位与ACK | 能按时序解释发送方和接收方 |
| 1.3 | 理解字节、页与容量 | 能解释地址31为何是第0页末尾 |
| 1.4 | 串起指定地址读、写后等待和跨页写 | 能区分总线传完与内部写完 |

这些小步可穿插到代码学习中；讲过不等于已经验收掌握。

**任务顺序：**

1. 区分选择芯片的设备地址与选择芯片内部位置的存储地址。
2. 确认容量、地址格式、页大小和写后等待要求。
3. 划分 BSP 与 APP：BSP 保证读写流程，APP 决定存什么、何时存，以及数据的业务含义。

**思考问题：** 地址用两个字节发送是否等于有 64 KB 容量？总线传输结束是否等于内部写入结束？电流校准值与编码器零点应该由哪一层解释？

**完成标准：** 能说明设备地址、存储地址、页大小、内部写周期分别影响什么。此步不要求写代码。

## 第 2 步：建立头文件基础框架

**设计目的：** 建立模块对外入口，让其他文件可以安全包含它。

**逐轮小步：**

1. **2.1 防重复包含**：自己建立保护结构；检查开始和结束是否配对。
2. **2.2 类型依赖**：引入接口所需类型；检查是否把私有资源误放进头文件。

**任务顺序：** 处理重复包含 → 判断接口所需类型来自哪里 → 引入必要依赖。

**思考问题：** 头文件中哪些内容供 APP 使用？设备地址、私有硬件信息和实现代码是否需要对 APP 暴露？

**完成标准：** 重复包含不产生重复定义，接口需要的类型可识别，私有实现留在 `.c`。

## 第 3 步：定义对外状态类型

**设计目的：** 让 APP 理解操作结果，不必依赖底层 HAL 的具体表达。

**逐轮小步：**

1. **3.1 结果分类**：列出成功、错误、超时、非法参数各自代表什么。
2. **3.2 类型定义**：自己写状态类型；检查名称、语法和默认枚举值。

**任务顺序：** 列出原工程需要区分的结果 → 确定统一表达方式 → 自己定义类型。

当前需要表达：成功、一般错误、超时、参数非法。

**思考问题：** 这是一次调用的结果，还是持续记录传输进度的状态？与 MT6816 的异步状态管理有什么不同？

**完成标准：** 四类结果完整，命名与工程一致，能解释各自用途；不为模仿 MT6816 额外添加运行状态机。

## 第 4 步：规划七个公共接口

**设计目的：** 先确定 APP 能要求驱动做什么，再由你设计调用方式。

按以下功能逐个规划，每轮只设计一个或一组紧密相关的接口：

**逐轮小步及当前函数名：** 不预先给参数、返回值或完整声明，先由你设计，再核对工程调用。

| 小步 | 功能名 | 本轮目标与检查点 |
| --- | --- | --- |
| 4.1 | `BSP_EEPROM_Init` | 设计硬件绑定；区分HAL句柄与寄存器类型 |
| 4.2 | `BSP_EEPROM_CheckConnection` | 设计配置后的通信检查；不把应答成功当作完整驱动验收 |
| 4.3 | `BSP_EEPROM_WaitReady` | 设计有期限的等待；说明预算如何指定、结果如何告知APP |
| 4.4 | `BSP_EEPROM_ReadByte` | 设计单字节读取；区分存储位置与结果变量位置 |
| 4.5 | `BSP_EEPROM_WriteByte` | 设计单字节写入；解释为什么输入数值副本已经足够 |
| 4.6 | `BSP_EEPROM_Read` | 设计连续读取；明确起点、接收空间与总字节数 |
| 4.7 | `BSP_EEPROM_Write` | 设计连续写入；表达源数据不应被驱动修改 |
| 4.8 | 核对完整头文件 | 检查接口顺序、类型和APP兼容性；参数中的数组写法不会创建接收数组 |

本轮已按用户要求将旧名 `BSP_EEPROM_IsReady` 改为 `BSP_EEPROM_CheckConnection`，同步了活动APP调用。读取历史资料时按职责识别旧名，不恢复旧名称。

| 顺序 | 功能 | 职责与设计问题 |
| --- | --- | --- |
| 1 | 绑定硬件 | 让驱动知道使用哪一路 I²C。哪些信息必须长期保存？与底层外设初始化如何分工？ |
| 2 | 探测就绪 | 判断器件当前是否应答。APP 需要怎样理解探测结果？ |
| 3 | 等待就绪 | 在有限时间内等到器件重新应答。如何区别单次探测和总等待过程？ |
| 4 | 连续读取 | 从指定位置取出一段数据。位置、数量、结果存放空间由谁决定？ |
| 5 | 连续写入 | 保存一段数据。哪些属于调用方需求，哪些页处理细节应留在驱动内部？ |
| 6 | 单字节读取 | 方便 APP 读取一个字节。如何与连续读取保持一致？ |
| 7 | 单字节写入 | 方便 APP 保存一个字节。是否需要重复设计底层流程？ |

**完成标准：** 七项功能都有声明；你能解释每项参数和返回值的设计理由，区分操作结果与实际数据。完成后再核对原工程命名、签名和 APP 调用，不预先给完整声明作为答案。

## 第 5 步：建立实现文件的私有资源

**设计目的：** 准备后续读写所需的固定配置和运行时硬件信息。

**逐轮小步：**

| 小步 | 本轮目标 | 检查点 |
| --- | --- | --- |
| 5.1 | 包含自己的头文件 | 使用本模块的公共类型和声明 |
| 5.2 | 配置设备地址 | 区分7位地址与当前HAL使用的左移形式 |
| 5.3 | 配置容量和页大小 | 明确单位都是字节，用于范围检查和写入拆分 |
| 5.4 | 配置普通通信与连接检查 | 区分通信超时和HAL内部尝试次数 |
| 5.5 | 配置写后等待 | 区分单轮探测次数、单轮超时与总预算 |
| 5.6 | 保存私有I²C句柄 | 长期保存HAL句柄地址、只在本文件可见、初始未绑定 |

**当前就在5.6。** 这一轮只定义私有变量，不开始函数实现。自己决定类型、作用域和初值；检查生命周期是否满足后续调用，当前不需要中断共享状态。

**任务顺序：** 包含自己的头文件 → 整理配置 → 确定长期保存的资源 → 设计作用域和初始状态。

**思考问题：** 哪些是固定配置，哪些是 APP 绑定的信息？保存外设寄存器信息和保存 HAL 句柄有什么区别？当前阻塞方案是否需要异步缓冲区或中断共享状态？

**完成标准：** 所需资源齐全，私有内容留在 `.c`；能解释生命周期与作用域，不机械添加 `volatile` 或异步数组。

## 第 6 步：统一转换 HAL 状态

**设计目的：** 避免每个读写函数重复解释底层通信结果。

**逐轮小步：**

1. **6.1 规划转换规则**：先对照HAL结果和BSP分类，说明哪些结果合并处理。
2. **6.2 实现私有工具**：自己设计并实现；检查完整分支、内部可见性和复用位置。

**任务顺序：** 列出底层可能结果 → 对照 BSP 的结果分类 → 设计一个模块内部共用的转换工具。

**思考问题：** 哪些情况需要单独区分？原版如何处理 HAL_BUSY？这个工具是否需要对 APP 公开？它是否需要修改调用方的数据？

**完成标准：** 转换规则与参考方案一致，普通错误和超时可区分，读写能够复用。另行核对原版就绪探测的结果处理，不擅自统一所有接口行为。

## 第 7 步：实现初始化接口

**设计目的：** 建立 APP 与 BSP 的硬件绑定关系。

**逐轮小步：**

1. **7.1 对照声明建立函数框架**：检查定义与头文件一致。
2. **7.2 保存硬件信息**：写入前面定义的私有资源；检查保存的是地址而非误取对象内容。
3. **7.3 解释调用链**：从APP传入到后续使用走一遍；确认这里没有通信和芯片在线保证。

**任务顺序：** 核对 APP 提供的硬件信息 → 保存供后续操作使用 → 明确此操作不承担的职责。

**思考问题：** 保存句柄是否等于配置 I²C 外设？绑定成功是否能证明芯片在线？未绑定时，后续操作应该如何处理？

**完成标准：** 能解释绑定信息的生命周期；不在这里额外读写 EEPROM 或重复初始化外设。

## 第 8 步：实现器件就绪探测

**设计目的：** 在正式读写之前，提供可通信性检查。

这里实现的当前函数名是 `BSP_EEPROM_CheckConnection`；保留本节标题以兼容已有Obsidian锚点。它不要求每次读写前重复调用。

**逐轮小步：**

1. **8.1 未绑定分支**：先处理没有可用硬件信息的情况；检查是否在调用HAL前退出。
2. **8.2 探测调用**：必要时查HAL接口，使用设备地址、连接检查尝试次数和通信超时。
3. **8.3 表达结果**：对照原版成功/失败规则，明确失败不等于芯片损坏。
4. **8.4 纸面事件链**：从APP调用到HAL尝试、应答和返回走一遍；成功时无需尝试满3次。

**任务顺序：** 确认绑定信息可用 → 发起就绪探测 → 按原版规则向 APP 表达结果。

**思考问题：** 探测失败是否一定代表芯片损坏？地址错误、断线、内部写入未结束能否单凭这次结果区分？一次 HAL 探测操作是否一定只有一次尝试？

**必要时的提示：** 查找 HAL 中用于判断设备是否应答的功能，而不是用读取数据代替探测。

**完成标准：** 有明确成功和失败路径；不访问数据内容，不把“不应答”直接解释成“芯片坏了”。

## 第 9 步：实现写后等待就绪

**设计目的：** 处理“总线已经传完，但芯片内部尚未写完”的阶段。

**逐轮小步：**

1. **9.1 设计出口**：先列出未绑定、预算非法、就绪、超时等分支；未完成循环前不运行此函数。
2. **9.2 建立时间基准**：规划开始时刻和已耗时计算，考虑计数回绕。
3. **9.3 单轮短探测**：每轮让HAL尝试1次，使用5ms超时配置；不调用配置为3次尝试的连接检查函数。
4. **9.4 完成有限循环**：成功立即退出，失败后检查总预算；检查是否有无限等待路径。
5. **9.5 解释时间边界**：20ms预算由写入调用方使用，5ms不是固定延时，实际退出可能略晚于预算。

**任务顺序：** 定义等待边界 → 记录时间 → 重复短探测 → 设计成功和超时出口。

**思考问题：** 为什么确认应答比固定延时更贴合这个需求？单次通信超时与总等待预算有什么区别？系统计时不推进会怎样？检查预算时是否可能已经超过期限？

**必要时的提示：** 查找 HAL 的毫秒计时功能与设备就绪探测功能，再自行组织流程。

**完成标准：** 不无限等待；能解释 ACK 轮询和实际等待上限。阻塞等待不进入高速电流环中断，计时依赖系统 tick 正常推进。

## 第 10 步：实现连续读取

**设计目的：** 把指定范围的数据放到 APP 提供的空间，并可靠报告整次操作结果。

**逐轮小步：**

1. **10.1 参数与范围检查**：先拒绝未绑定、空空间、零长度和越界；说明检查顺序与溢出问题。
2. **10.2 规划分块状态**：明确已经读取多少、还剩多少、本轮读取多少；先纸面推演。
3. **10.3 实现一轮传输**：必要时查HAL，区分设备地址、EEPROM内部位置和RAM接收位置。
4. **10.4 失败与推进**：只有本轮成功才推进偏移；失败后不能把部分数据当整段有效。
5. **10.5 闭合循环与复盘**：到总长度时完成；用长度1、32、33和末尾边界检查流程。

**任务顺序：** 检查调用条件和访问范围 → 规划分块 → 维护存储位置与接收位置 → 处理失败和完成。

**思考问题：** 驱动能否仅从指针知道数组容量？如何避免范围检查中的算术溢出？分块后两个位置如何同步推进？中途失败时，已读数据应该怎样理解？

**必要时的提示：** 查找 HAL 中带内部存储地址的读取功能；核对“设备地址”和“内部地址”各自对应的字段。

**完成标准：** 不越过器件容量，分块数据落在正确位置。原版每次最多读 32 字节，这是代码安排，不是读取必须服从页写边界。

## 第 11 步：实现跨页拆分写入

**设计目的：** 避免页写越界造成同页覆盖，并保证每段写后确认就绪。

**逐轮小步：**

1. **11.1 写前检查**：复盘读取的范围检查，明确源数组只读约束。
2. **11.2 页边界推演**：先算当前页剩余空间，再确定本段长度；不先给出完整计算代码。
3. **11.3 实现一段写入**：必要时查HAL写接口；核对两个地址和当前源数据位置。
4. **11.4 接上写后等待**：传输成功后才能等待内部写完；给定总预算，分别处理通信失败与等待失败。
5. **11.5 推进并闭合循环**：两阶段成功后才推进；用非页首起点检查每轮都不跨页。
6. **11.6 复盘部分完成**：解释前段成功、后段失败时的存储状态，不宣称整段原子回滚。

**任务顺序：** 检查范围 → 确定当前页可写空间 → 规划本段长度 → 写入并等待 → 推进到下一段。

**思考问题：** 总长度小于一页是否就能一次写完？如何根据当前地址找出页内位置？什么条件满足后才能推进偏移？中途失败是否代表此前什么也没写？

**纸面练习：** 根据页大小，自己推算从地址 30 写 6 字节、从页首写 33 字节、从 `0x1FBF` 写 64 字节各应怎样分段。实现前先解释拆分理由。

**必要时的提示：** 查找带内部存储地址的 HAL 写入功能，复用前面设计的写后等待功能。

**完成标准：** 每段不跨页、每段写后等待、存储位置与数据位置同步推进。不修改 APP 的待写数据；必要的类型兼容处理在调用边界核对。失败不保证整段未写入，返回成功也不代表做过读回比较。

## 第 12 步：封装单字节读写

**设计目的：** 通过复用已有读写能力，提供方便的单字节入口。

**逐轮小步：**

1. **12.1 封装单字节读取**：复用连续读取，检查结果如何到达APP变量。
2. **12.2 封装单字节写入**：复用连续写入，检查局部输入数据在阻塞调用期间的生命周期。
3. **12.3 对照结果路径**：确保底层失败传回APP，没有重复HAL流程或额外等待。

**任务顺序：** 把单字节需求对应到连续读写 → 判断所需数据的生命周期 → 完成封装。

**思考问题：** 为什么不再写一套 HAL 操作？读取结果与写入数据在调用关系上有什么不同？局部数据在阻塞调用期间是否有效？如果以后改成异步，原设计还能否直接使用？

**完成标准：** 复用范围检查、页处理和写后等待，能解释数据如何传递，以及为什么生命周期足够。

## 第 13 步：验证边界和 APP 调用

**设计目的：** 确认功能复原完整，再讨论性能和扩展。

**逐轮小步：**

1. **13.1 功能与调用核对**：对比保存基线，检查7个公共功能、私有工具和改名后的APP调用。
2. **13.2 离线编译**：确认完整模块后再编译；修复必要问题，保持原工程配置。
3. **13.3 边界推演或有针对性的验证**：覆盖容量末尾、跨页和超时出口，记录证据。
4. **13.4 审查APP写测试**：确认备份、测试、恢复的区域和失败处理；未满足安全条件不进行硬件写入。
5. **13.5 有条件的实机验证**：保持PWM关闭，记录通信、读回和恢复结果；与编译结果分开。
6. **13.6 学习复盘**：记录理解与调用关系，再把原版待优化项单独列出，不混入复原验收。

**任务顺序：**

1. 对比原版功能和声明，区分遗漏、复原错误与原版待优化项。
2. 编译检查接口一致性，保持原芯片和编译器。

5. 条件具备后做实机验证，最后再整理笔记与关系图。

**验证清单：**

- 空句柄、空数据指针、长度为 0、起始地址 8192、整段超过末尾。
- 地址 8191 读写 1 字节与 2 字节的范围差异。
- 非对齐地址跨页、页首写超过一页、每段写后等待。
- 原 APP 多字节测试从 `0x1FBF` 开始，长度为 1、16、32、33、64；逐项解释为何这样选择。
- 传输失败或等待超时后的部分完成行为。
- 测试前备份，写后读回比较，恢复后再读确认。

**安全边界：** EEPROM 写测试会改变非易失数据。实机前确认测试区域不含校准值或重要参数，检查供电和总线，按实际器件封装核对写保护配置；本轮阅读的WLCSP4手册无WP引脚，不套用其他封装引脚。电机 PWM 保持关闭。断电或恢复失败仍可能留下测试数据，不反复上电执行写测试代替只读检查。

**完成标准：** 功能对比清楚、编译通过、边界行为可解释；实机验证另行记录，不把编译通过当作硬件验收。

## 工程参考约束

以下是原工程复原时的核对依据，不是完整实现答案。设计时先说明理由，再回看配置与调用。

| 项目       | 当前参考方案                           |
| -------- | -------------------------------- |
| 器件       | BL24C64A                         |
| 设备地址     | 7 位 `0x50`；当前 STM32 HAL 使用左移一位形式 |
| 容量与存储范围  | 8192 字节；`0x0000～0x1FFF`          |
| 内部地址传输   | 两个地址字节；不等于 65536 字节容量            |
| 页大小      | 32 字节                            |
| 常规通信超时   | 100 ms                           |
| 就绪探测尝试次数 | 3 次                              |
| 等待中的单次探测 | 1 次尝试，5 ms 超时                    |
| 写后等待预算   | 20 ms                            |
| APP 绑定   | 工程使用 `hi2c1`                     |
| 调用位置     | 初始化/适当的非高速控制路径，不进入 16 kHz 电流环    |

20 ms 是代码的等待预算，不是器件固定写入时间；5 ms 是单次超时配置，不是每次必须延时的时间。器件协议要求与软件配置需要分开核对。

**当前宏及对应事件：**

| 宏 | 值与单位 | 使用目标 |
| --- | --- | --- |
| `EEPROM_DEVICE_ADDRESS` | `0x50U << 1` | 联系指定芯片 |
| `EEPROM_PAGE_SIZE` | 32字节 | 规划不跨页的写入段 |
| `EEPROM_CAPACITY_BYTES` | 8192字节 | 检查整段范围 |
| `EEPROM_TIMEOUT_MS` | 100ms | 普通通信与连接检查的HAL超时配置 |
| `EEPROM_READY_TRIALS` | 3次 | `CheckConnection`的一次HAL调用最多尝试次数 |
| `EEPROM_POLL_TRIALS` | 1次 | `WaitReady`每轮HAL调用尝试次数 |
| `EEPROM_POLL_TIMEOUT_MS` | 5ms | `WaitReady`单轮HAL探测超时配置 |
| `EEPROM_WRITE_TIMEOUT_MS` | 20ms | 写入方交给`WaitReady`的总等待预算 |

事件顺序：初始化绑定 → 连接检查；写入时先完成总线传输，再开始写后等待。100ms和20ms约束不同阶段，不互相包含，不是固定延时，也不能当作完整操作的严格最大耗时。`WaitReady`直接做短HAL探测，不调用`CheckConnection`；连接检查不要求每次读写前执行。

## 复盘：与 MT6816 的不同点

MT6816 重点是两段 SPI 读取、异步生命周期、状态机和完成回调。当前 EEPROM 重点是两类地址、范围检查、页边界和写后等待。

EEPROM 原版执行路径：APP 调用 → BSP 检查并分块 → HAL 阻塞传输 → 写操作确认就绪 → BSP 向 APP 报告结果。不要为沿用 MT6816 写法而添加不需要的异步资源。
